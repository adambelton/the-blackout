## Dual-Kairos discovery — full debrief

### Symptom

User-reported during broadcast: "Matchroom and moderator console are missing generations that are in the inspector." Initially hypothesised as ElevenLabs/Hume audio synthesis failure.

### Investigation path

1. Started with localhost — no live activity because the live test was running remotely.
2. Pulled the runtime logs and spotted **two distinct instance IDs in narrative-generation lines**, each generating its own narratives interleaved by seconds.
3. The runtime inventory confirmed that two instances had been created seconds apart by the same release event.

### Root cause

Each Kairos instance maintains its own in-memory enrichment pipeline (`waitingRoom`, recent-cycles buffer, state tracker). A load balancer distributed feed-entry HTTP pushes between them, so each instance processed only the entries it received and generated narratives independently from its disjoint subset.

The shared Postgres receives writes from both — narratives, cycles, feed entries all persist. The inspector reads from DB → sees both machines' output.

The Blackout's `subscribeFeed` WS connects to **one** machine (whichever the load balancer routes the WS upgrade to). Narratives broadcast over that machine's WS reach the conductor. Narratives generated on the other machine are persisted but never broadcast on the Blackout's connected socket → conductor never receives them → matchroom/moderator never see them.

### Why the state existed

- The configuration declared a minimum of one instance, but a minimum is a floor rather than an exact target.
- Both Kairos instances were created seconds apart by a single release event.
- The Blackout server used equivalent runtime settings but had only one instance, making initial provisioning the relevant difference.
- **The mental model that bit us:** minimum-count configuration did not reconcile an existing higher count. Scaling down required an explicit runtime operation.
- **Most likely root cause:** high-availability defaults provisioned two instances at application creation, and later releases updated both without reducing the count.

### Fix applied

- The extra Kairos instance was removed explicitly.
- Blackout's `[kairos-client] feed WS closed (code=1006) — reconnecting in 1000ms (attempt 1)` followed by `feed WS reconnected after 1 attempt(s)` 1 second later.
- All subsequent narratives reached the conductor. Matchroom + moderator unblocked.

### Permanent guard

The singleton requirement and the minimum-versus-target distinction were documented beside the runtime configuration.

## Findings (7) observed during the broadcast

Numbered for cross-reference. Priority is the user's call but a recommended order is in "Recommended next moves" below.

### Finding 1 — Cold-start lead-time gap

**Symptom:** First few passages of the broadcast had visible gaps between them. Steady-state was smooth — gappy only at the beginning.

**Hypothesis:** The lead-time goal is to deliver each new passage to the client 10–15s before the current passage's audio ends, so the client always has the next passage queued. At cold start there's no "current passage" to overlap-deliver against — the first generation has to land before any audio plays at all, and there's no buffer.

**Steady-state principle:** total end-to-end latency from current-passage audio-start to next-passage delivered ≤ `(current_duration_ms − 10_000ms)`.

**Cold start is a separate sub-question.** Possible mitigations to explore:
- Pre-generate a scene-setting passage ahead of kickoff (warming-window output, already designed in match-windows memo)
- Bias the first 2–3 passages toward shorter durations to "build the buffer"
- Defer matchroom audio start until ≥1 passage is queued (silent intro, intentional)

**Priority:** Lower — affects only the very start; once running, the steady-state is good.

### Finding 2 — Canonical-events spoiler leak

**Symptom (two confirmed reproductions):**
- Greenwood YELLOW_CARD: announced in cycle 64 prose ("The yellow card will follow Greenwood now…"), event entry actually drained into cycle 66's chunk → 2 cycles inverted.
- Coffey YELLOW_CARD: announced in cycle 78 ("Then Coffey alongside her"), event entry drained into cycle 80 → same shape.

**Root cause:** `apps/kairos/server/src/narrative/engine.ts:350-352` builds `canonicalEvents` from `allEntries` (the full broadcast feed) without any drain-boundary filter:

```ts
const canonicalEvents = allEntries.filter(
  (e) => e.sourceCanonical && e.sourceType === "event",
);
```

The 60s content-time DELAY rule applies to chunk_entries (curation drain) but **not** to the canonicalEvents preamble. The system prompt (`generator.ts:22`) tells the generator that canonical events are "ground truth — never omit an event the canonical events list reports when it would be relevant." So a freshly-arrived YELLOW_CARD becomes ground truth from the next cycle onward, even while still in the waiting room.

**Three-passage chronological smear per goal/card:**
- Cycle N: card visible in canonicalEvents (just arrived) → prose mentions it (anticipation/foreshadowing — feels hallucinated)
- Cycle N+1: card entry drains from waiting room → prose covers the event
- Cycle N+2: card now in canonicalEvents AND past → prose may reference again

Listener hears about consequences before hearing the event itself.

**Fix path:** Filter `canonicalEvents` at `engine.ts:350` by the same content-time boundary the cycle's chunk drain used:
- **Option 1 (clean):** Pass drain-boundary ordinal through `RunInputs`. Filter `canonicalEvents` to `entryOrdinal(e) <= drainBoundary`. Pipeline already knows the boundary at flush time; just plumb it through.
- **Option 2 (loose):** Wall-clock proxy — `e.timestamp <= now() - delayMs`. Doesn't require new field plumbing but doesn't perfectly align with content-time drain.

Option 1 is correct.

**Priority:** High — user-visible quality hit on every goal/card, very reproducible.

### Finding 3 — Phase cue wall-clock fanout (HT in extra time)

**Symptom:** Sportmonks fired HALFTIME at 11:48:06 UTC. Matchroom UI immediately flipped to HT view. But the audio narrator was still covering pre-whistle action (cumulative lag through Sportmonks → audio commentary → distillation → cycle drain → generation → synthesis → playback). Listener saw "HT" while hearing first-half stoppage-time narration.

**Root cause:** `apps/blackout/server/src/conductor/RoomConductor.ts:330-349` `transitionTo` runs `fanOut({ type: "phase" })` synchronously when the conductor observes the HALFTIME entry. Wall-clock, not playback-clock. The matchroom's UI swaps state on receipt.

This violates the no-spoilers principle (memory `project_matchroom_no_spoilers`) — UI rendered correct state vs. data, but spoiled the audio experience.

**Fix path:** The phase transition should ride a cover marker on the closing passage's whistle moment, not on the conductor's wall-clock observation of the HALFTIME entry. Subsumed by the universal cover-marker reveal gate design (see Design Direction A below).

**Priority:** High — user-visible spoiler, principle-level violation.

### Finding 4 — Post-whistle audio mis-stamped

**Symptom:** After the HALFTIME signal at 11:48:06, distilled audio commentary about pre-whistle action ("Shaw finds space on the left and sends a shot that Falk parries away", "Holland sends a lovely cross into the box", "Yamashita made an excellent save against Denise O'Sullivan's effort") arrived at Kairos with `phase=halftime, phaseSecond=0` — ordinal collision with the synthetic HALFTIME marker. They describe first-half action but are filed as halftime content.

**Root cause:** `apps/blackout/server/src/lib/broadcast-runner.ts pushEntry` stamps each entry with `getPhaseAnchor()` reflecting the runner's current phase at push time, not the audio's content time. The events adapter's anchor advances to halftime as soon as Sportmonks fires HALFTIME. Distillation that arrives a few seconds later (audio lag) inherits the now-halftime anchor even though it's narrating pre-whistle play.

**Fix path:** Distillation entries should carry phase + phaseSecond reflecting **the audio's content time**, not the runner's current anchor. Two approaches:
- The distiller passes `atWallClockMs` matching the audio chunk's wall-clock time. The runner already has this hook (`pushEntry` accepts `atWallClockMs`). Verify the distiller is using it correctly during the post-whistle window.
- Alternative: stamp distillation entries with the content time inferred from the audio's chunk timestamp minus the radio-offset estimate.

**Priority:** Medium — contributes to Finding 5 (closing prose inversion) and pollutes halftime cycles.

### Finding 5 — Closing prose chronological inversion

**Symptom:** The phase-flush closing passage at 11:50:18 UTC opened with the whistle then circled back to cover the closing action: "The whistle goes, and the Joie Stadium lets out a breath it wasn't sure how to hold. Goalless. But the scoreline is almost beside the point. Liverpool hit the post from a corner. Yamashita flung herself to deny O'Sullivan…" Whistle announced before the action that led to it.

**Root cause (combined):**
- The synthetic HALFTIME marker sits in the cycle's chunk_entries with the highest ordinal among first-half-and-marker (ordinal 2_000_000). The LLM treats its prominent presence as the dominant moment and opens on it.
- `formatFeedContext` at `apps/kairos/server/src/narrative/generator.ts:148-202` does **not sort entries by content ordinal**. It iterates `ctx.entries` in arrival order. Even if entries were correctly stamped, they wouldn't appear in content-time order in the feed listing presented to the LLM.
- Plus the mis-stamping from Finding 4 — post-whistle audio collides with the marker at ordinal 2_000_000, so even with sorting they could appear after.
- The phase-flush cycle runs with **no closing-shaped prompt**. Only the deferred consumer-prompt cycle (HALFTIME_REFLECTION_PROMPT) gets framing. The phase-flush itself uses the regular generation prompt.

**Fix path (three layers):**
1. **Sort `ctx.entries` by content ordinal** in `formatFeedContext` (or upstream when building the cycle's chunk). HALFTIME's high ordinal lands last in the listing.
2. **Fix the post-whistle stamping (Finding 4).** Then the marker is uncontested as the highest ordinal.
3. **Attach a closing-shaped prompt to the phase-flush cycle.** "Narrate the closing action chronologically; land on the whistle as the final beat." Currently only the consumer-prompt cycle gets framing.

After 1 + 2, the marker is structurally last. Layer 3 is polish.

**Priority:** High — user-flagged as awkward; happens at every halftime/full-time transition.

### Finding 6 — Random HT-middle narrative

## Design direction

Three pieces, agreed during this session. Each subsumes specific findings.

### A. Universal cover-marker reveal gate (revealed/revealing canonical state)

The matchroom UI is driven by the conductor's canonical state. To uphold the no-spoilers principle (nothing visible before the narrator has spoken it), state must split into two:

- **Revealed canonical state** — facts already past their anchor, or facts that never had one (pre-match brief, narrative voice, broadcast metadata). Safe to render immediately on entry to this set.
- **Revealing canonical state** — facts with a pending cover marker on a generated passage. Flip into revealed only when audio playback crosses the marker's `charOffset`.

**The cover-marker mechanism IS the universal reveal gate.** Each narrative passage carries `covers: [{ ref, charOffset }]` listing every state-affecting thing it touches. When audio playback crosses a cover's charOffset, all reveal channels fire together for that cover: event card in ribbon, scoreline update, illustration swap, phase indicator change. Same gate, every channel.

Example: a goal cover with marker at charOffset 240 means until audio crosses character 240, the listener has not "received" the goal. None of {event ribbon chip, score tick, celebration image, HT/FT badge if applicable} appear before that moment. Cross the marker, all reveal in unison.

#### API contract — per-passage canonical-state split

Each passage carries two canonical-state objects:

```ts
type Passage = {
  // ...existing (text, narrationId, audio_url, batchContentTime, …)
  revealedCanonical: CanonicalState;         // state safe to render at passage start
  revealingCanonical: CanonicalState;        // state this passage will reveal, with marker offsets per field
};
```

`CanonicalState` is the union of all reveal channels: `score`, `phase`, `matchMinute`, `events[]`, `illustration`, `lineup`. Fields in `revealingCanonical` carry their `markerOffset` (charOffset within prose) so the consumer knows when each reveals.

**Consumer logic (same for matchroom + render):**

1. On passage receipt, render `revealedCanonical` immediately.
2. As audio playback advances, watch each marker offset in `revealingCanonical`.
3. On crossing a marker, move that field into visible state.
4. By audio end, `revealingCanonical` is empty; the next passage arrives with this passage's reveals baked into ITS `revealedCanonical`.

Render pipeline does the same walk, frame-by-frame:
```
visible_state(T) = revealedCanonical + { each revealingCanonical field whose markerOffset <= T }
```

**The per-passage split is the API boundary.** The conductor doesn't expose global current-state; it sends a stream of passages each carrying their own state delta. Browser and renderer reconstruct global state by walking the stream. Deterministic; no render-specific reveal logic.

#### State authority — live vs replay

Same data shape both modes. Authority over "current playback position" differs.

**Live mode — server-authoritative.** Server is source of truth for (a) which passage is currently live, (b) `playbackStartedAt` (server-anchored timestamp). Both already exist on `RoomConductor.currentlyPlaying`. Every connected client derives the same audio offset (`Date.now() - playbackStartedAt`) and runs the same reveal computation locally. Convergence is guaranteed by the shared anchors — no per-marker reveal cues needed.

**Replay mode — client-authoritative.** Client owns the audio element entirely. Server has no visibility into any replay user's position. Each user is independent (pause, resume, navigate away). The reveal computation is the same function fed a different offset.

```
revealed_state(offset) = passage.revealedCanonical + markers_crossed_at(offset)
```

- Live: `offset = Date.now() - server.playbackStartedAt`
- Replay: `offset = localAudioElement.currentTime`

#### Late-joiner scenario (load-bearing motivation)

The motivation for this design is the late joiner: someone opens the matchroom at minute 67, mid-passage. The matchroom must render the current state immediately and continue revealing from there.

**The current passage IS the cached state snapshot.** No history replay, no bootstrap-by-walking-events.

For a late joiner at audio offset 12s of a 35s passage:
1. Server sends current passage with audio offset.
2. Client renders `passage.revealedCanonical` immediately — full state at passage start (every goal so far, current scoreline, minute, phase, lineup, last illustration).
3. Client applies each marker in `passage.revealingCanonical` whose offset ≤ 12s of audio elapsed.
4. Audio continues; remaining markers fire as crossed.

Self-consistent chain property:
```
passage[N+1].revealedCanonical  ==  passage[N].revealedCanonical  +  passage[N].revealingCanonical
```

#### Validation against current API contract

Today's `NarrativeOutput` (`apps/kairos/server/src/narrative/types.ts:95-127`) and `NarrativeCue` (`apps/blackout/server/src/conductor/types.ts:138-163`) have:

- ✅ `covers: [{ entryId, contentTime?, charOffset? }]` — the marker mechanism for events
- ✅ `batchEntryIds` — full superset (events not in covers reveal at audio-end fallback)
- ✅ `batchContentTime` — match clock (snaps at audio start = pre-revealed canonical)
- ❌ `revealedCanonical` / `revealingCanonical` bundle — NOT in contract
- ❌ Score — derived client-side from `revealedEvents`, not in contract
- ❌ Phase — separate `PhaseCue` (`type: "phase"`), wall-clock fanout, NOT cover-anchored
- ❌ Illustration — attached to `NarrativeOutput.imagery`, no charOffset
- ❌ Lineup — not represented

The mechanism exists (covers + charOffset works for events); the API just needs to bundle it into a single canonical-state object that every channel passes through.

#### Convergence work to land the model

1. **Generator** — extend `NarrativeOutput` with `revealedCanonical` + `revealingCanonical`. Existing `covers[]` becomes a sub-detail of `revealingCanonical.events`. `batchContentTime` migrates into `revealedCanonical.matchMinute`.
2. **Phase moves out of standalone cue** into the passage's `revealingCanonical.phase` with marker offset. The `PhaseCue` retires.
3. **Illustration moves into covers** with charOffset. The `imagery` field can stay (production decision) but reveal timing moves to a marker.
4. **Score becomes explicit** in revealed/revealing canonical. The matchroom's `deriveScore` from `revealedEvents` retires — it was filling a gap the contract should fill directly.
5. **Lineup added** as a new channel.
6. **Matchroom client** stops maintaining its own `revealedEvents` set + score derivation; consumes `revealedCanonical` (immediate) + walks `revealingCanonical` against audio playback.
7. **Render pipeline** does the same walk, frame-by-frame.

#### Subsumes findings 3 (phase cue wall-clock) and partly 4 (illustration timing)

Once the universal gate ships, phase no longer flips before audio reaches the whistle moment. Illustration swaps land at the marker, matching matchroom + render.

### B. Render pipeline — auto-render on broadcast complete

Every broadcast at `complete` triggers a render job that produces a fixed set of artefacts from existing materials (narration audio in R2, prose text in DB, illustrations in R2, match metadata).

#### Artefact set

| Artefact | Format | Audience | Where it goes |
|---|---|---|---|
| Full broadcast video | 16:9 .mp4, illustrations + prose captions over audio | Writer keepsake; Blackout archive | R2; signed URL emailed to writer + admin downloads |
| Highlight reel | 16:9 .mp4, 3–5 min | General sharing | R2; team Twitter/Reels post |
| Social clips | 9:16 .mp4, 30–45s, captions + watermark | TikTok / Reels / Twitter | R2; clip library in admin |
| Full broadcast audio | .mp3 (128kbps mono target), ID3 chapters per narration | Podcast feed; general audio share | R2; referenced from RSS |
| Podcast RSS feed | XML | Apple Podcasts, Spotify, Pocket Casts | `/podcast/feed.xml` from `apps/blackout/server` (or web) |

#### Decisions

- **One Blackout show, not per-writer feeds, for MVP.** Writer credited in episode `<itunes:author>` + description. Per-writer feeds fork later — episode metadata already carries writer attribution.
- **Rendering runs as an isolated job** — an ephemeral environment per render. Stateless, spiky workload can scale to zero and remains cleaner than embedding rendering in `apps/blackout/server`.
- **Trigger: auto on `complete`** with a moderator-facing "re-render" admin button for template changes.
- **Chapters from narrations.** Each `broadcast_narrations` row → ID3 chapter frame. Title from `batchContentTime` + a short label from prose. Uncommon premium feature in football podcasts.

#### Reveal-fidelity & chrome decision

**Principle: chrome rules differ by format.** Browser is interactive — chrome supports glancing (event ribbon, chip animations, dense info). Video is passive — chrome supports immersion (full-frame imagery, minimal overlay). Audio is auditory — chrome is chapters.

Video render is a translation of the matchroom for a different medium, not a literal port.

**Social clips** — atomic format, no reveal logic needed (whole clip plays as one punch).

**Full broadcast video + highlight reel** — chrome:

| Element | In video? | Treatment |
|---|---|---|
| Prose | Yes | Paragraph-level fade-in at audio anchors, bottom-third caption |
| Illustrations | Yes | Full-frame, Ken Burns push-in (start scale 1.0 → end ~1.05–1.10). One image per passage. Transitions are **cover-anchored, not boundary-cued** — previous passage's image lingers briefly into new passage's audio, swaps at the cover anchor. Push-in spans `(this passage's image anchor)` to `(next passage's image anchor)`, crossing the audio seam. Visual rhythm deliberately offset from audio rhythm for cinematic effect. |
| Score | Yes | Persistent corner overlay, updates at audio anchors (matches matchroom no-spoilers gate) |
| Match minute | Yes | Persistent corner overlay, advances with batchContentTime |
| Phase indicator (HT/FT) | Yes | Shows at audio-anchored moments — same anchor as the matchroom UI flip |
| Event chips / event ribbon | **No** | Cut from video chrome entirely — competes with immersion |

Per-character strike animation (matchroom flourish) is dropped — doesn't survive video compression well and adds disproportionate render cost.

### C. Passage lead-time target

Each new narrative passage should be delivered to the client **10–15 seconds before the current passage's audio finishes playing**, so the client always has the next passage queued and the seam between passages is silent-gap-free.

**Why:** matchroom plays passage audio sequentially; if the next passage isn't yet at the client when the current ends, there's an audible silence gap. With ~30–45s passage durations, that's a 25–35% surface for gaps. Pre-delivery converts the seam into a hard cut and removes the dependency on round-trip latency at the moment of playback.

**How to apply:** tune the cumulative pipeline (Kairos generation → Blackout synthesis → fanOut to client) so total end-to-end latency from current-passage audio-start ≤ `(current_duration_ms − 10_000ms)`. Today the cycle-timing logs show generation alone at ~30s; synthesis adds more on top. Closing the gap likely needs:
- Kairos cycle cadence aligned to passage duration (already partly in pacing service)
- Synthesis kicked off as soon as text arrives, not gated behind anything
- Possibly speculative pre-fetch of the next cycle's enrichment while the current is in synthesis

**Cold-start sub-question:** smoothness from the very first passage is the specific weakness — first cycle has no prior passage to overlap-deliver against. Cold-start design is a separate sub-question from steady-state lead-time. See Finding 1 for mitigation hypotheses.
