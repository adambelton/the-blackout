# packages/blackout/shared — the Blackout side's types hub

`@blackout/shared`. Every shape the Blackout's server and web both touch lives here, declared once: the WebSocket cue contracts the server emits and the web consumes, the per-passage canonical-state bundle the matchroom walks, the broadcast/event/match-time/radio-source/user/pipeline-cycle types, plus the type guards and the pure match-time helpers that *must* agree between the two (the server and the matchroom both order events the same way only because they call the same `compareEventsByMatchTime`). A change to one of these fails `tsc` in `apps/blackout/server` and `apps/blackout/client` — that's the point. It's a types-and-pure-helpers package: no runtime dependencies, no I/O, no framework. **`apps/kairos/server` does not consume this package** — the seam between Kairos and the Blackout is the HTTP/WS wire, not shared TypeScript; see *How it fits*.

For where this sits and how the Blackout's two apps use it, see [`../README.md`](../../README.md) and [`apps/README.md`](../../../apps/README.md). This README goes one level deeper.

Two seams to hold onto:
1. **The Kairos boundary.** `@blackout/shared` is the *Blackout side's* types hub — `apps/blackout/server` and `apps/blackout/client`. `apps/kairos/server` does not depend on it or import from it; the seam between Kairos and the Blackout is the HTTP/WS wire (`apps/blackout/server/src/lib/kairos.ts`), not shared TypeScript. A shape genuinely needed on both sides is **duplicated**, not shared — and it's almost always Kairos that owns it (it's the engine; the Blackout is the consumer): Kairos owns its API enums, the Blackout side mirrors them here (`pipeline-cycle.ts` is exactly that — the consumer-side mirror Kairos never imports back; the longer-term direction is to lift it into a Kairos-owned types package the Blackout imports). There is no "domain-agnostic subset Kairos may import" carve-out — if Kairos needs a type, it defines it. (`match-time.ts` is no exception: the inner function parses football's clock — `"45+2"` / `"HT"` / `"FT"` — so it's the Blackout's reading of Kairos's subject-time string, shared by the server and the matchroom, both Blackout. Kairos has its own `clampMonotonicMinute` on its side. See [`../../docs/vocabulary.md`](../../../docs/vocabulary.md) § Time for the three-domain model; the file keeps the `match-time.ts` name as a Blackout-side domain label even though the inner function is `parseMatchTime`.)
2. **The WS cue contract.** The cue *shapes* are declared here so `apps/blackout/server` (the emitter) and `apps/blackout/client` (the consumer) type the same wire format — drift fails `tsc` on one side or the other. (Mid-migration caveat: the *bundle* cues — `passage_*`, `MatchroomCue` — are in `passage.ts`; the *legacy* cues the matchroom still consumes — `narrative`/`play`/`illustration` — aren't in `@blackout/shared`; Sub-piece 4 retires the legacy ones, at which point the matchroom cue contract is exactly `passage.ts`.)

## What it does

A flat barrel (`types/index.ts` — `export *` of every file; `.js` extensions because the package is ESM, resolved to the `.ts` at compile/dev time) over twelve files:

- **`broadcast.ts`** — the heaviest: `Broadcast` (the row shape — `homeTeam`/`awayTeam`/`competition`/`matchDate`/`status`/`fixtureId`/`radioSourceId`/`ttsVoiceId`/`ttsEnabled` (the TTS kill switch, persisted on the legacy `tts_autoplay` column)/`moderatorId`/`kairosBroadcastId`/`matchBrief`), `BroadcastStatus` (`draft/scheduled/live/complete/archived` + `isBroadcastStatus`), `BroadcastPhase` (the conductor FSM — `pre_ramp/warming/live_first_half/halftime/live_second_half/full_time_winddown/complete` + `isBroadcastPhase` + `LIVE_PHASES`/`isLivePhase` — declared once here, the conductor re-exports it), `TeamSide` (`home/away` + `isTeamSide`), `BroadcastTtsProvider` (`openai/elevenlabs/hume` + labels + `isBroadcastTtsProvider`), `TtsVoiceRecord`, `BroadcastViewEvent`, `BroadcastView`/`BroadcastViewArchive`/`ArchiveNarration`, `ModeratorView`/`ModeratorFeedEntry`, `CreateBroadcastInput`, and **`SOURCE`** — the typed source-name constants (`matchEvents`/`matchPressure`/`matchStats`/`matchAction`/`moderator`/`narrativeContext`/`narrativeVoice`), hoisted here from `apps/blackout/server` (the audit's "magic-string source names" failure — the typed accessor needs to be reachable from any app).
- **`events.ts`** — `MatchEventType` (the Sportmonks-derived event types — `GOAL`/`OWN_GOAL`/`PENALTY`/`SUBSTITUTION`/`YELLOW_CARD`/`RED_CARD`/`SECOND_YELLOW`/`VAR`/…), `GameplayTransitionEventType` (the synthetic phase whistles — `KICKOFF`/`HALFTIME`/`SECOND_HALF_KICKOFF`/`FULL_TIME`; in shared because the matchroom renders them in the ribbon, the conductor owns the runtime semantics), `CanonicalEventType` (the union of the two — `CanonicalEvent.eventType`), `MatchEvent`.
- **`canonical-state.ts`** — the matchroom reveal architecture (Design A, 2026-05-03 cluster): `CanonicalEvent` (a match event in matchroom-display form, carries the entry's subject time via `subjectTime` — see § Time), `CanonicalState` (the visible-state snapshot — `score`/`phase`/`contentMinute` (the consumer's content-minute label)/`events`/`illustration` (`imageKey` durable + `imageUrl` re-resolve-every-read)/`lineup` (reserved null)), `RevealingMarker<T>` (`{value, charOffset?}` — no offset = audio-end reveal), `RevealingCanonical` (`{events?, phase?}` — score + contentMinute deliberately not channels: score is a client-side projection over revealed goals, contentMinute snaps at passage start), and the **pure state-fold** `applyRevealingCanonical(state, revealing)` + `emptyCanonicalState(phase?)` — used by the conductor (fold each passage's revealing forward → the next passage's `revealedCanonical`), the matchroom client + render pipeline (project visible state by walking only the markers whose `charOffset` audio has crossed), and the backfill script. The chain invariant: `passage[N+1].revealedCanonical === applyRevealingCanonical(passage[N].revealedCanonical, passage[N].revealingCanonical)`.
- **`passage.ts`** — `Passage` (the wire bundle — `narrativeId`/`narrationId`/`text`/`wordCount`/`generatedAt`/`audio`/`playback` (server-anchored — `startedAt`+`serverNow`; null in replay)/`revealedCanonical`/`revealingCanonical`) + the bundle WS cues (`ConnectedCue` with `currentPassage`, `PassageAddedCue`, `PassageAudioReadyCue`, `PassageStartedCue`, `PassageSkippedCue`, `PassageUpdatedCue`, `BroadcastStatusChangedCue`, `GenerationSkippedCue`) + `MatchroomCue` (the union). The lifecycle is documented inline: `passage_added` → `passage_audio_ready` → `passage_started` → (client `audio.onended` — *not* a server cue) → next `passage_added`.
- **`match-time.ts`** — `parseMatchTime(value)` + `compareEventsByMatchTime(a, b)`. **Football clock parsing** — `"45+2"` / `"HT"` (45.5) / `"FT"` (9999) are football conventions; this is the Blackout's reading of Kairos's subject-time strings, shared by `apps/blackout/server` and the matchroom (both Blackout) so they order events identically; drift here is a subtle UI bug. Kairos has its own `clampMonotonicMinute` on its side of the seam — *not* this; the parallel implementations are deliberate, not a merge target. The file keeps the `match-time.ts` name as a Blackout-side domain label (see § Kairos boundary above). (Also re-implemented server-side as `composeContentMinute`'s comparator — tracked tech-debt.)
- **`pipeline-cycle.ts`** — the consumer-side **mirror** of Kairos's API output shapes (the comment says so): `PipelineTriggerReason` (`accumulation/external`), `PipelineFlushTrigger` (`cadence/phase/consumer_prompt`), `PipelineCycleTimingMs`, `PipelineCycleDrift`, `PipelineCycleSummary`/`Detail`/`Entry`/`Annotation`/`Curation`/`CurationDecision`/`CurationConflict`, `PipelineImageryDecision`, `BroadcastHealth`, `PipelineGeneration`. Read by `apps/blackout/server`'s inspector routes + `apps/blackout/client`'s inspector page. **Never imported by Kairos** — Kairos owns the enums these mirror; this is the Blackout's copy. (This file is the model for "duplicate, don't share, across the Kairos seam"; the longer-term direction is to lift it into a Kairos-owned types package the Blackout imports — tracked in [`../../apps/README.md`](../../../apps/README.md) § Open work.)
- **`radio-source.ts`** (`RadioSource`), **`fixtures.ts`** (`UpcomingFixture`/`LiveFixture`), **`user.ts`** (`UserRole` — `writer/admin` + `isUserRole`/`isAdmin`; stored on the Better Auth `users.role` column, set server-side by the user-create hook, `input: false` so client values are ignored), **`schedule.ts`** (`collectScheduleBlockers(b)` — the `draft → scheduled` prereqs: match brief non-empty, fixture set, radio source set, a voice if `ttsEnabled`; single source of truth for the server's 422 *and* the moderator UI's blocker list), **`service-status.ts`** (`ServiceStatus` — `{name, status: ok|error|unconfigured, message?}` — the server's health-check rows, rendered in the moderator console; used by `apps/blackout/server` + `apps/blackout/client` only).

`tests/` — the pure-helper coverage: `match-time.test.ts`, `schedule.test.ts`, `matchroom-cue-roundtrip.test.ts`, `canonical-state.test.ts`, `type-guards-and-records.test.ts`.

## Contract

### Provided
- The types — the wire/contract shapes for the Blackout side: web↔server WS cues + the `BroadcastView`/`ModeratorView` DTOs; the canonical-state bundle the conductor composes and the matchroom walks; the consumer-side mirror of Kairos's API output (`pipeline-cycle.ts`) the inspector reads. The constants (`SOURCE` the source names; `BROADCAST_*` / `TEAM_SIDES` / `USER_ROLES` / `LIVE_PHASES`). The type guards (`isBroadcastStatus` / `isBroadcastPhase` / `isTeamSide` / `isBroadcastTtsProvider` / `isLivePhase` / `isUserRole` / `isAdmin`). The pure helpers (`parseMatchTime` / `compareEventsByMatchTime` / `applyRevealingCanonical` / `emptyCanonicalState` / `collectScheduleBlockers`).
- **The boundary contract:** this is the Blackout side's package — `apps/blackout/server` + `apps/blackout/client`. `apps/kairos/server` does not consume it; cross-seam shapes are duplicated (Kairos owns its API enums; the Blackout side mirrors them in `pipeline-cycle.ts`), never shared via this package. The cue *shapes* are the wire contract — server and web type the same thing or `tsc` fails.

### Depended on
- Nothing at runtime — types-and-pure-helpers only, no I/O, no framework. `drizzle-orm` is *not* a dep here (the schemas are in `apps/blackout/server`/`apps/kairos/server`/`@blackout/auth`, not this package). Builds to `dist/types/` via `tsc`; `apps/blackout/server` and `apps/blackout/client` resolve `@blackout/shared` via the workspace (`apps/kairos/server` has no dependency on it). Tests run with `tsx --test`.

## Anti-patterns

- **No `@blackout/shared` import from Kairos.** `apps/kairos/server` has no dependency on this package and imports nothing from it — the seam is the HTTP/WS wire. Don't reach for a sub-barrel or a "domain-agnostic" carve-out to "let Kairos in"; a shape needed both sides is duplicated (the `pipeline-cycle.ts` mirror is the pattern), and Kairos defines its own copy.
- **No drift between the cue declarations and the emitter/consumer.** A cue shape change here that one side doesn't follow fails `tsc` — keep it that way; don't widen a cue to `unknown` to dodge the check (the audit's "WS-cue type-safety gap" — the conductor's `ConductorCue` union was tightened from an `unknown`-bearing escape hatch precisely so a missing entry fails the build).
- **No re-implementation of the shared pure helpers** *within an app* that's allowed to drift. `parseMatchTime` / `compareEventsByMatchTime` exist here so `apps/blackout/server` and the matchroom agree; the server-side `composeContentMinute` comparator re-implements that ordering inside `apps/blackout/server` — a tracked duplication. (Kairos's `clampMonotonicMinute` is on the *other* side of the seam — separate by design, per "duplicate, don't share"; not the same kind of debt.)
- **No shadowing of a shared union by an app-local one with a different value set.** `BroadcastStatus` is shadowed in `apps/blackout/server`'s + `apps/kairos/server`'s db `enums.ts` (different values) — a tracked collision; don't add more.

## Open work

- **`BroadcastStatus` / `ConnectedCue` name collisions** — `BroadcastStatus` shadowed by both apps' db enums (different value sets); `ConnectedCue` declared here (`currentPassage`) *and* in `apps/blackout/server/src/conductor/types.ts` (legacy, `currentPlay`), both on the `connected` cue today. Tracked in [`../README.md`](../../README.md) § Open work.
- **The matchroom cue contract is mid-migration** — the bundle cues are here; the legacy `narrative`/`play`/`illustration` cues the matchroom still consumes aren't; Sub-piece 4 retires the legacy ones. → [`docs/matchroom-reveal-architecture-scoping.md`](../../../docs/matchroom-reveal-architecture-scoping.md).
- **`pipeline-cycle.ts` is a hand-maintained mirror.** It tracks Kairos's API output shapes by hand; a Kairos-side change to those shapes has to be re-typed here. Longer-term: lift it into a Kairos-owned types package the Blackout imports (Kairos owns its contract; the Blackout consumes it — no hand-mirroring). Cross-app; tracked in [`../../apps/README.md`](../../../apps/README.md) § Open work. (The earlier "partition the barrel into an engine-agnostic sub-barrel" plan was dropped — Kairos doesn't consume this package at all, so there's nothing to partition for it; see [`docs/codebase-audit-2026-05-10.md`](../../../docs/codebase-audit-2026-05-10.md).)
